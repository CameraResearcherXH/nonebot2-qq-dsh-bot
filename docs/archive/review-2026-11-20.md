# 全项目体检报告（2026-11-20）

> 目的：回答三个问题 —— **有没有 bug / 有没有设计矛盾 / 该怎么改**。
> 方法：通读自研代码（services 50 个模块 + plugins 15 个插件，约 3.9 万行；node.py 4.5k；scripts 1.5w），
> 逐个核对 docs/agent-pipeline.md 的宣称与代码实现，并抽查 data/ 下的真实运行数据。
> 结论按「先锐评 → 再证据 → 最后改造路线」组织。

---

## 0. 一句话锐评

**这不是一个「没写大纲」的项目，而是一个「有 12 份互相覆盖的大纲、但没有一份是权威」的项目。**

代码本身不烂 —— 注释质量、踩坑记录、前缀缓存意识、ContextVar 修并发、离线自检体系，
都远超一般个人项目。真正的问题不是「写得差」，而是：

> **同一个概念被实现了 2~4 遍，每一遍都只对了一半；而所有失败都被 279 个 `except Exception` 吞掉，
> 所以你既不知道哪一遍在生效，也不知道哪一遍坏了。**

于是每加一个功能就要「再打一层补丁」，补丁之间互相不知道对方存在 —— 这才是「摸不着头脑」的来源。
摸不着头脑不是因为系统复杂，而是因为**系统里有多个互相矛盾的事实源，且没有一个能告诉你真相**。

## 2. 六个结构性矛盾（这才是「摸不着头脑」的根因）

### 矛盾 1：没有「一个大脑」，有 5 个各自为政的决策器

同一句群消息，可能被这些互不知情的决策器同时处理：

| 决策器 | 位置 | 依据 |
|---|---|---|
| `_need_reply` | chat:1819 | 正则 + 白名单 + 关注会话 + 高刷 |
| `_random_chat_loop` | chat:4565 | 心情 × 亲密度 × 查看频率 + `aura_logic.decide_group_reply` |
| `vision_agent` | priority=5, block=True | 图片必回（绕开 `_need_reply`） |
| `sticker_intent` | priority=2, block=True | 「收/存 + 表情」自然语言 |
| `_proactive_private_loop` | chat:6053 | 主动私聊的另一套闸门 |

**后果**：`REPLY_INTERVAL`、`BURST_MSG_COUNT`、冷却、静音这些闸门，每条路径各写一遍、各漏一处。
真机上「刚回完又插一句」「同一条回两次」「让她安静她还说」这类问题，几乎都源于此。

### 矛盾 2：同一份对话存了 7 份，没有一份是权威

一条群消息会被写入：

1. `data/memory.db`（sqlite，`add_memory`，短期历史）
2. `data/dialogue/*.jsonl`（`dialogue_log`，原文）
3. `data/memory/index.json` + `blocks/*.json`（`memory_v2` 的 event 记忆）
4. `recent_group_msgs`（chat 内存 deque）
5. `group_scene._STORE`（现场/线程）
6. `data/state/*.json`（`conv_state` 压缩状态）
7. `data/profiles/*.json`（bond 相处印象）

**后果**：
- 修 bug 时你必须先搞清楚「这条链路读的是第几份」；
- 重启后各份的补齐策略不同（`_db_history` / `seed_from_log` / `recent[:-1]`），于是出现「重启就变傻」；
- **`_db_history` 把所有历史 user 行都标成「当前说话人的名字」**（`llm.py:768` 用同一个 `who`），
  重启后群聊上下文会集体串人 —— 这和「分清谁在说话」的核心设计直接对立。

### 矛盾 3：prompt 在 6 个地方拼，且「固定区」并不固定

一次群回复最多有 **十几条 system 消息**：

`persona 文件（9,600 字）` → `_behaviour_protocol`（▍00~▍11） → `build_prompt` 背景段 →
`build_packet` 的 8 个块（profiles/memory_index/lore/yesterday/revisit/library/mood/quiet） →
`conv_state` → `历史对话` → `focus_card` → `expression` → `lore_post` → `_dynamic_protocol` →
`_post_rules` → `群聊总结` → `当前消息`。

而「固定区」里塞了**会变的内容**：

- `_sticker_protocol()` 里写了 `表情库共 N 张`（`llm.py:2317`）→ 每收一张表情，全站前缀缓存失效；
- `_length_rule(key)` 按群读 `group_tuning` → 每个群的前缀都不同（可接受，但要知情）；
- `attention.render()` 读的是模块级常量（没问题，但同一份「风格规则」在 persona 文件里又写了一遍）。

**后果**：你以为在吃 1/10 缓存价，实际上经常整段 miss；而且「哪条规则在生效」没人能一眼看出 ——
persona 文件里写的、`_behaviour_protocol` 里写的、`_post_rules` 里写的，三处可能互相矛盾。

### 矛盾 4：关键路径串行 3 次 LLM，旁路再挂 4 个，没有预算/队列

一次普通群回复的真实耗时构成：

```
scene_auditor.audit_recent   ← await，timeout 6s   （chat:3845）
  → referee.preflight (GLM)  ← await，timeout 2.5s （chat:3955，REFEREE_PREFLIGHT=true）
    → call_llm (DeepSeek)    ← 最多 6 轮工具 + N 轮补资料
      → 发送（含 _wait_group_quota 最多等 15s、气泡延迟最多 4.5s）
```

同时后台还在跑：`mood_judge`（20s 一次）、`conv_state.update`（5 分钟一次）、
`expression.mine`、`profile_miner.mine`、`referee` 影子回答。

**后果**：p99 延迟 = 6 + 2.5 + 30 + 15 ≈ **50 秒**；token 成本 = 主调用 + 1 次 GLM + 1 次审核 + 若干旁路。
**没有任何全局并发上限、预算上限或优先级**。而且这两次「辅助 LLM」在**关键路径上同步等待**，
是「她回得很慢」最直接的原因。

### 矛盾 5：一个仓库装了两个程序，音频算法写了两遍且已经漂移

`bot.py`（香港容器）和 `node.py`（上海算力机）是两个独立程序，共享一个仓库、共享一份「约定」，
但**不共享代码**：

| 逻辑 | 服务器版 | 算力机版 | 状态 |
|---|---|---|---|
| `pitch_for_range` | `services/song_gender.py:67` | `node.py:1221` | ❌ **已经漂移**：算力机有「男声按 p50 对齐 220Hz、下限 6 半音」的修复（2026-11-12），服务器版没有 |
| `pitch_from_f0` | `song_gender.py:135`（`target_f0`, `gender`） | `node.py:1999`（`gender`, `target_f0`） | 签名/分支都不同 |
| `estimate_f0` / `analyze_f0` | `song_gender.py` | `node.py:1834/1945` | 两份自相关实现 |
| `_extract_json` | —— | `node.py:2508` **和** `node.py:3648` | ❌ 同名重复定义，后一个覆盖前一个（见 Bug #5） |

**后果**：同一首歌，服务器算一个 pitch，算力机算另一个；谁生效取决于任务走哪条分支。
注释里那句「与算力机 node.py 的 pitch_for_range 保持一致」，是**靠人肉记忆维持的一致性** —— 这是必然要坏的。

### 矛盾 6：`Rule` 里带副作用，于是「谁 block 了谁」决定上下文丢不丢

`chat = on_message(rule=Rule(_need_reply), priority=10, block=False)`，而 `_need_reply` 干的全是**副作用**：

- `chat_switch.maybe_thaw`（破冰）
- `_enrich_text`（语音转写、转发卡片抓取、链接预览、引用展开 —— **网络 IO**）
- `dialogue_log.log_msg` / `recent_group_msgs.append` / `group_scene.observe`
- `_maybe_mood_watch` / `expression` 计数
- `_note_dislike`（被嫌弃 → 静音）

**后果**：
- 任何 `priority < 10 && block=True` 的插件（`vision_agent`、`sticker_intent`、`tool_dispatcher`、`draw.wait_img`…）
  一旦命中，**这些副作用全部不执行** → 上下文缺口，而她下一轮完全不知道刚才发生了什么；
- 规则本应是「纯判断」，现在却做网络请求，是「加一个插件就多一个丢上下文的口子」的结构性原因。

## 4. 为什么会打成这样（机制性原因，不是能力问题）

1. **需求以「真机一句话」的形式到来**（「这图笑死」「她怎么又说了」），每次都用最小补丁接住；
   补丁没有「归属」，于是 `chat/__init__.py` 变成所有补丁的公共垃圾场（8,628 行）。
2. **没有可观测的失败**：279 个 `except Exception` 让 90% 的 bug 表现为「她就是有点怪」，
   而不是「报错了」。于是你只能靠猜，猜错就再打一层补丁 —— 补丁数量指数增长。
3. **配置无 schema**：339 个 key 靠人记，代码默认值和 `.env` 值谁生效全靠运气（见 Bug #8）。
4. **自检体系很强，但校验的是「模块自己」**：1,743 项自测能证明「函数没坏」，
   证明不了「A 的输出真的进了 B 的输入」。`audit_pipeline.py` 是对的方向，但只有 14 关，
   覆盖不了上面 6 个矛盾。
5. **没有版本控制**：无法「先重构再对比行为」，只能「原地改 + 祈祷」。

## 5. 改造路线（按投入产出排序，建议照做）

### 阶段 0：止血（半天，不改架构）

   **轮换所有已进过镜像/仓库的 key**（DeepSeek / GLM / DashScope / Tavily / API_SECRET / COVER_API_KEYS）。
2. `git init` + `.gitignore`（`.env`、`data/`、`napcat/`、`plugins_backup/`、`__pycache__/`、`venv/`），
   先提交一个「原样快照」，之后所有改动都可 diff。
3. 删死代码：`services/reply.py` + `vision_agent` 的 import、`node.py` 第二个 `_extract_json`、
   `MAX_REPLY_CHARS`、`bot.py.working`、`.env.working`、`plugins/grok_chat.py.bak`。
4. 修 P1 里成本最低的三个：#5（删重复函数）、#8（`.env` 改 16）、#10（`limit_hanzi` 加「非汉字也按字符封顶」）。
5. `napcat_tools.execute()` 加一条硬闸：`group_id` 不在 `ALLOWED_GROUPS` 一律拒；`send_private_msg` 的
   `user_id` 不在 `ALLOWED_PRIVATE ∪ 群成员` 一律走「问主人」。**这条比什么都重要**。

### 阶段 1：把「一条消息的一生」收进一个模块（1~2 天，收益最大）

目标：`_need_reply` 变**纯函数**，副作用集中到一处。

```
services/pipeline.py
  ├─ observe(event)      # 唯一的「记账」入口：dialogue_log + group_scene + recent + 计数
  ├─ should_reply(event) # 纯判断：白名单/睡眠/指令/媒体/关注/高刷（无 IO、无副作用）
  └─ handle(event)       # 审计 → 预检 → call_llm → parse → 发送（一个函数，但分段清晰）
```

- `chat` 的 matcher 规则改为 `Rule(pipeline.should_reply)`；
- 所有插件（含 vision_agent）先调 `pipeline.observe()`，谁 block 都不会丢上下文；
- 决策器合并：`_random_chat_loop` / `_proactive_private_loop` 都走 `pipeline.decide(kind="interject")`，
  **共用同一套闸门和同一份状态**（冷却/额度/静音/关注期）。

### 阶段 2：上下文「单一事实源」（2~3 天）

- 以 `dialogue_log` 为**唯一**原文源（append-only，jsonl 就够）；
  `recent_group_msgs` / `group_scene` / `conv_state` / `memory_v2 event` 全部降级为**它的视图/缓存**，
  重启时统一从它重建，删掉 `_db_history` 那套「按当前说话人补名字」的假数据路径。
- `data/memory/index.json` 换 sqlite（`memories(id, ts, kind, about_qq, gid, summary, tokens_json, importance, emotion_weight, status)`），
  建 FTS5 或至少 `about_qq`/`created_at` 索引；**不要**每次全量 dump。
  这一步单独就能把每条消息的 CPU 从 ~200ms 降到 ~5ms。
- profiles 写入合并成一次（`upsert+style+bond` 一个事务），并挪到 `asyncio.to_thread`。

### 阶段 3：LLM 网关（2 天）

```
services/gateway.py
  - 统一 provider 表（deepseek/glm/qwen/local/agent），统一超时、重试、并发信号量
  - 分优先级：interactive（主回复）/ background（审核、判读、压缩、挖矿）
  - 全局预算：每分钟 token / 每小时调用次数，超了 background 直接丢弃
  - 关键路径只允许 1 次 interactive 调用：
      · scene_auditor / referee.preflight 改为「上一轮结果的异步补充」，
        不再挡在本次回复前面（或至少 default off，A/B 验证有收益再开）
```

### 阶段 4：拆 `plugins/chat`（1~2 天，纯搬运，不改行为）

## 6. 明确不建议做的事

1. **不要**再往 `_need_reply` 里加正则/关键词判断。`aura_logic` 注释里用户自己说过
   「不要用正则去唤醒，LLM 本身就是智能判断」—— 这条原则应该贯彻到所有决策点。
2. **不要**继续加「第 7 份对话副本」。要加新视图，先从 `dialogue_log` 派生。
3. **不要**在没有 git 的情况下做大重构。先 `git init`，否则任何重构都不可回滚。
4. **不要**为了「更真实」再加第 3 个辅助 LLM 到关键路径。辅助模型只能在**离线/影子**通道跑。
5. **不要**把 `plugins_backup` / `napcat` / `data` 留在工作目录里当「备份」—— 那是 1.6 GB 的噪音，
   真正的备份是 git + 定期 `data/` 快照。

## 8. 最后

这套系统的**想法**是好的：五层自我、按需拉取、前缀缓存、静默权、破冰、翻页提示 ——
这些是很多「AI 群友」项目没有的深度，而且注释里那些「真机踩过」的记录，本身就是资产。

它现在的问题，是一个**成功项目的典型中年危机**：功能长太快，边界没跟上。
不需要推倒重来 —— 需要的是**把已有的 12 份真相收敛成 1 份**，
然后让失败重新可见（少吞异常、多留证据）。做完阶段 0~2，你会重新「摸得着头」。
