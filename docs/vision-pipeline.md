# 识图链路：画面描述 + 搜图源 → 角色扮演模型总结

> 用户 2026-11-22 的设计：
> 「看到图，给角色扮演 API，API 同时给搜图源插件和识图 LLM，
>  然后以两边的结果（一个是识图描述，一个是搜图源和角色）来总结回复图片消息。」

## 0. 决策（2026-11-25）

| 项 | 决策 | 理由 |
|---|---|---|
| **本地角色库** | **不建** | `trace.moe / SauceNAO / Ascii2D / IQDB` 已是云端源；本地图库维护成本高 |
| **角色名怎么来** | 云端元数据（作品/作者/角色 tag）+ 视觉模型 + 轻量别名表 | 云端源多数只给作品/作者，不直接给角色名 |
| **域** | 只做**动漫/插画**，不做真人脸 | 合规/隐私风险 |
| **算力** | 重活放**算力机异步任务**（GPU）；bot 只编排 | bot 只有 2C/3.4G，无 GPU |
| **优先级** | **暂缓**，排在 P0~P9 之后 | 先把主链路/检索/情绪做完 |

> 不建本地库 ≠ 不建任何表：仍需一张很小的 `character_alias`
> （角色 ID / 名字 / 别名 / 作品 / 来源），从云端元数据回填，**不含图片、不含 embedding**。
> 这样「叫出角色名」靠的是元数据 + 视觉模型，不是本地以图搜图。

## 1. 现在的流程（as-built）

```
QQ 图片消息
  │
  ├─ plugins/vision_agent.process_image()
  │    ├─ 取图（url / get_image / 本地文件）
  │    ├─ GIF → 抽 6 帧拼一张网格图（视觉模型读不了动图）
  │    └─ services/vision_verify.recognize()
  │         ├─ 指纹缓存命中 → 直接复用（同一张图不重复花钱）
  │         ├─ ① trace.moe（动漫截图 → 番名/集数/角色）
  │         ├─ ② qwen-VL 结构化识图（画面 / 类型 / 文字 / 角色猜测）
  │         ├─ ③ GLM-4V 结构化识图（第二意见）
  │         ├─ ④ 多源搜图（**新增**）SauceNAO / Ascii2D / IQDB，和 ②③ 并行
  │         ├─ ⑤ 联网核验（只有前几层给了专名才查，防幻觉）
  │         ├─ ⑥ 定向追问（还没名字时换个问法再问一次）
  │         └─ ⑦ 拼成多源报告 report
  │
  └─ report → fake_text（VISION_TAG）→ chat 队列 → 角色扮演模型
       fake_text 里包含：
         · qwen识图 / GLM识图（画面描述，各一行）
         · trace.moe（番名/集数/相似度/角色候选，或"没有可靠命中"）
         · 搜图源（SauceNAO/Ascii2D/IQDB 的标题/相似度/作者）
         · 联网核验（一致 / 不一致 / 未核验）
         · 【这张图】是发给谁的（她 / 某人 / 看不出）
         · 图配文字时的那句话
         · 「不要在回复里复述画面」
```

## 2. 为什么两边都要

| 来源 | 强项 | 弱项 |
|---|---|---|
| 视觉模型（qwen / GLM） | 画面、构图、文字 OCR、表情含义 | 专名（角色/作品）幻觉率高（实测 ~60%） |
| trace.moe | 动漫截图的番名/集数，拿画面比对帧库 | 只对动漫截图有效；插画/网图/糊图不行 |
| SauceNAO / Ascii2D / IQDB | 插画/网图的原始出处（Pixiv/Twitter） | 对动漫截图一般；有速率限制 |

所以报告是**证据清单**，不是结论：让角色扮演模型自己判断哪个可信，
冲突时以画面为准，相似度低只当线索。

## 3. 成本控制

- 图片指纹缓存：同一张图只认一次（转发/复读不重复花钱）；
- 多源搜图只在 `VISION_EXTRA_SEARCH=true`（默认开）时跑，**和视觉模型并行**，
  失败/超时静默跳过；
- 联网核验只在「前几层给了专名」时才查；
- 定向追问只在前几层都没给名字时问一次。

## 4. 相关开关（.env）

```bash
TRACE_MOE=true                # 动漫截图以图搜番
VISION_EXTRA_SEARCH=true      # 多源搜图总开关
VISION_EXTRA_ENGINES=saucenao,ascii2d   # 默认只跑快的两个
#   IQDB 实测 40s+，会拖住图片回复；要用自己加进上面这行

                              # 不配的话 SauceNAO 基本返回空

VISION_TARGETED_ASK=true      # 没名字时定向追问一次
VISION_VERIFY=true            # 专名联网核验
```

## 6. 不许把画面描述念出来（2026-11-23）

用户反馈：「偶尔还是会发送出图片的描述。」真机两例：

- `【图片识别结果】啊……这个……` —— 识别标记直接漏给用户；
- `【图片】一只淡蓝色的卡通仓鼠双臂交叉抱在胸前，咧着嘴，一脸得意的样子。`
  —— 把她自己看到的画面描述整句念了出来，下一句才是真正的回复。

三层修法：

1. **提示词**（`plugins/vision_agent` + `services/llm.py` 视觉分支最后一条 system）：
   画面描述只给自己看，不要复述、不要写 `【图片】…`、不要报颜色/姿势/表情/背景细节；
   图里是题目/截图/文字信息时，**直接回答里面的问题**，不要念题干。
2. **输出层兜底**（`services/aura_logic.py::strip_media_echo`）：
   删掉 `【图片识别结果】/【视频解析结果】` 标记；以 `【图片】/【画面】` 开头的描述整条丢弃；
   结构化头（群号/发送者QQ/图片内容…）和 `qwen：/GLM：` 报告行整行丢弃。
3. **闸门**：`audit_features` 新增 G19；`selftest_all` / `test_new_features` 各加 3 项断言。

实测（容器内真实调 DeepSeek）：

| 场景 | 回复 |
|---|---|
| 仓鼠表情包 | 哦？跟我摆谱呢 |
| 数学题截图 `3x+5=20` | 3x = 15，x = 5 |
| 聊天截图「我害怕」 | 害怕啥 |
| 橘猫躺键盘 | 好家伙 这么会挑地方睡 / 键盘都给你占了 |

4 个场景都没有出现 `【图片】`、识别标记或照抄描述。
