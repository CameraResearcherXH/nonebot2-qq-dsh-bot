## 1. 身份混淆：保留我们的人称处理，加「核对层」提正确率

**不取**：MaiBot 的人称/画像候选机制（我们 target 五分类 + 标签 + 档案已覆盖）。
**取**：0729 §3.3 的**证据核验条件**与 person-migration 的**冲突保留语义**——作为校验规则。

### 1.1 写入核对（治 about_qq 失准，A1 的落地）
- 判读归因按已定 target 五分类走（about_qq 由 target 决定，不再一律 speaker）；
- LLM 填的 about_qq **必须过硬核对**（借 0729 核验条件简化）：
  ① 该 QQ 在本群真实存在（roster/entities）；② 与消息的 speaker/@对象/回复对象之一一致，
  或文本中明确提到；③ 非 bot 自身。核对不过 → 落 `about_qq=''` + 标签保留，**不猜**；
- 别名写入（A 修复硬逻辑 learner）同样带证据：evidence_msg_ids 必须真实存在、
  自述（speaker==主体）→ direct，他述 → reported/uncertain，冲突 → conflicted 双方保留。
  字段加在我们已定的 entities.aliases JSON 里，**不建新表**。

### 1.2 读取核对（B 修复 + 防编造）
- 「X是谁/把X@出来」硬查档案：命中注入事实行（带权威措辞），未命中注入「没找到」；
- 注入前核对：别名→QQ 解析结果与当前群 roster 一致才注入（防跨群串名）。

### 1.3 正确率度量
- `data/logs/identity.jsonl`：每次归因/别名解析记 {输入, 判定, 核对结果, 是否被模型采用}；
  出错案例（如肥牛）可回放。**先有度量，再谈提升**。

## 2. 检索失准：先诊断断点，不抄他们的检索

**我们的情绪×时间曲线 + 说话人加权 + 档案协助理论上够好。出了问题是链路某环断了。**

### 2.1 六环诊断（先做，~60 行插桩 + 案例回放）
对失败案例（肥牛/淫魔/奏奏对话）逐环取证：
1. **写入环**：相关记忆的 about_qq/tags 当时填对了吗？（A1 嫌疑最大）
2. **查询环**：atmo 给的 queries/keywords 含人名/别名吗？alias→QQ 展开了吗？（§5 关键词工程未接）
3. **过滤环**：gid/status/时间窗把目标记忆滤掉了吗？（gid 修复后复验）
4. **排序环**：目标记忆进了候选但排在 limit=5 之外？（w_speaker 只在 about_qq 精确相等时生效，
   归因错→加权失效，与环 1 联动）
5. **注入环**：召回了但 prompt 位置/格式让模型没看见？
6. **采用环**：看见了但模型没用（被人格/硬规则压过）？

每环记 diag.jsonl（查询词、候选数、top5 id+score、注入字符数、模型是否引用）。
**诊断结论出来前不动打分公式。**

### 2.2 按断点修（预案，诊断后取舍）
- 环 1 断 → §1.1 写入核对（最可能）；
- 环 2 断 → 查询词 alias→QQ 展开 + 人名必进 keywords（我们 §5 已定，接上）；
- 环 4 断 → about_qq 空/错时按 tags.person 兜底加权（用我们已有标签，不换 BM25）；
- 环 5/6 断 → 注入位置/措辞调整（动态块后置，见 §3）。

### 2.3 档案协助的配合
- profiles.touch 候选 = 说话人 + @对象 + 回复对象（我们 target 五分类天然支持，~10 行）；
- 召回 miss 时档案事实行兜底注入（§1.2），**档案是检索的第二道墙**，不是替代。

## 3. token 与工具：做「工具检索与关键字工程」，不是披露机制

**用户定调**：动态调用 + 工具折叠一直在做；折叠后需要再翻找 → 问题是**选不准**，
要在 tool 的检索和关键字上做工程。

### 3.1 根因（已核实）
`_tool_score`（llm.py:471）= query 字符集 ∩ 描述字符集 的**单字符计数**。
中文高频字（的/我/看/图/发）让所有工具得分趋同，top-N 近似随机 → 该挂的没挂、模型翻找。

### 3.2 工程化（~100 行，改现有 _tool_score/tools_for，主干不动）
1. **词级匹配替字符级**：query 与工具 blob 都切中文二元组（bigram）+ 英文/数字整词，
   按词重合打分（我们 memdb 已有二元切词思路，复用）；
2. **每工具 curated 关键字/别名表**：`TOOL_KEYWORDS = {who: [是谁, 名字, 别名, QQ, 档案, 认识…],
   draw: [画, 生图, 头像…], sing: [唱, 翻唱, 歌…]}`——人工维护短表，命中权重高于描述重合；
   名字精确命中 > 关键字命中 > 描述词重合（三级权重）；
3. **atmo 意图直通**：atmo 输出已有 kind/queries，工具选择参考 kind（如 kind=person → who 必挂），
   减少纯文本匹配的盲区；
4. **选择日志与 miss 度量**：现有 [TOOLS] 日志加「模型实际调用了哪些/挂了没调/调了没挂」，
   identity.jsonl 同目录 tool_miss.jsonl；**用 miss 率驱动关键字表迭代**，不拍脑袋。
5. 折叠/翻找机制保留：未挂工具模型仍可通过既有翻找入口拿（主干不动），
   工程目标是把 miss 率压到不需要翻找。

### 3.3 prompt 成本（顺带，小改）
- 动态块（心情/记忆/conv_state/事实行）追加末尾保前缀缓存（aurabot/MaiBot 共识，~30 行）；
- 历史折叠工具调用+结果成对处理（AstrBot 思路，~30 行）；
- 常驻段裁剪：**先量各段 token 占比再定**（待用户确认清单）。

## 4. 算力机 qwen：降级方案可做，异步是硬约束

**用户批准**：atmo 独立角色 + 本地 qwen2.5:7b + 云 fallback。
**硬约束**：绝不阻塞消息路径。

### 4.1 异步设计（在现有 atmosphere 骨架上加固）
- 消息路径**只读缓存**：atmo 结果 TTL 缓存命中即用；未命中**不等**，走原闸门，
  后台 fire-and-forget 补算供下一轮（现有 async 骨架已是此模式，核实并补漏）；
- 后台任务带 ATMO_TIMEOUT（本地 7B 目标 ≤1.5s），超时即弃 + 显式记 fallback；
- 单飞（same gid 并发只算一次）+ 全局并发上限（防节点排队拖垮）；
- 节点在线判定用心跳（已修），离线直接云 fallback，**真实探测不假装就绪**（aurabot probe 教训）；
- /自检 可见：本地命中率、fallback 次数、平均耗时。

### 4.2 输出扩展
entities/teach_intent 字段只作 §1 核对层的**候选输入**，不直接写库（硬逻辑+核验为准）。

## 5. 主动发言：好感/情绪是「想不想说」，账本只管「这会儿让谁说」

**用户定调**：整体是好感/情绪驱动接话，融合是难题。**不引入外来驱动替换我们的**。

### 5.1 融合原则（两层分离）
- **欲望层（我们的，不动）**：decide_group_reply（好感/心情/冷却/额度）→ view_frequency（惯性）
  → [SILENCE]（静默唤醒）产出「她这会儿想不想说、多想说」；
- **机会层（新增薄账本，~80 行）**：只在**多个来源同时想说**时仲裁——
  插话/白月光借用/节点回报共享 gid 预算域，并发最多一个逻辑发言；
  节点长任务回报 = 委托因果，**优先保留**（不被插话挤掉）；
  发送 uncertain 不退款不自动重发（防双份打扰）。
- 账本**不产生发言欲望、不修改概率**——欲望仍 100% 来自好感/情绪链。
  被仲裁挤掉的来源不扣心情、不记「失败」，只是「这轮没轮到」（避免污染情绪驱动）。

### 5.2 为什么这样融合
aurabot 双引擎打架的教训是「两套欲望源竞争」；我们只有一套欲望源（好感/情绪），
账本是欲望之外的**机会调度**，不构成第二引擎，打架无从发生。

## 6. 工具/任务执行状态机（借他们的设计，落我们的执行路径）

**用户定调**：给 LLM 用工具/做任务加状态机与执行策略，参考他们的设计。

### 6.1 借来的语义（三家共识）
- AstrBot run_turn：**工具调用在执行前先持久化**；重启后缺失结果补「未知」，不装成功；
- AstrBot subagent：重启在途标 interrupted，**不自动重放**；结果回原会话；
- aurabot 账本：pending→sending→sent/failed/uncertain/expired；uncertain 不退款不重发；
- MaiBot schedule：持久化周期检查、重启补投递、**至少一次**（配合幂等键去重）。

### 6.2 落到我们的两处
1. **[[CALL]] 执行**（llm.py 工具执行处，~60 行）：
   `intent 落盘 → running → done/failed/uncertain`；执行前写 intent（含工具名+参数指纹），
   崩溃/重启后对账：有 intent 无结果 → 标 unknown 回给模型（「上次执行结果未知」），
   **不自动重跑**（防重复发图/重复扣费）；参数指纹幂等，同指纹短期重复调用直接拒。
2. **节点任务**（node.py + 回报处理，~40 行，用户自己运行验证）：
   任务状态同状态机；节点重启在途标 interrupted；回报走 §5 账本委托因果；
   翻唱/生图成品发送 uncertain 不重发。

### 6.3 执行策略
- L0 只读工具（who/recall/搜索）：自动，失败可重试；
- L1 写自己数据（remember/别名/conv_state）：自动 + 留痕；
- L2 外发/不可逆（send/生图/翻唱/节点任务）：状态机全程 + 幂等 + uncertain 不重发。
  （分级借 aurabot AUTONOMY-NOTES，只用于执行策略，不引入自治引擎。）
